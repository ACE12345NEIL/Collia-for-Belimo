# 1. PROJECT OVERVIEW

Collia is a Building Management System (BMS) configuration, data integration and intelligence platform being developed for BELIMO.

The objective is to allow users to:

1. Create a digital representation of a building.
2. Configure floors and rooms.
3. Add room-level HVAC equipment.
4. Add shared equipment independently of rooms.
5. Associate CSV filenames with individual equipment instances.
6. Place all corresponding CSV files in one designated directory.
7. Process the CSV files automatically using their configured filenames.
8. Extract equipment information, parameters and relationships.
9. Generate a Knowledge Graph representing the configured building and its HVAC infrastructure.
10. Detect anomalies in equipment operation.
11. Analyse probable causes.
12. Predict potential equipment failures.
13. Suggest possible corrective solutions.
14. Query the configured system and its findings using an offline LLM-based chatbot.

The building configuration created by the user and the actual information extracted from Belimo CSV files are the two primary inputs to this system.

The overall objective is to create a structured digital representation of a building that can support graph-based analysis, reasoning and intelligent querying.

# 6. CSV FILE MANAGEMENT — CORE FUNCTIONALITY

CSV integration is one of the most important features of Collia.

The user should not have to upload CSV files individually through the application.

Instead, implement a folder-based workflow.

## 6.1 Intended workflow

1. The user creates the building configuration.
2. The user creates floors and rooms.
3. The user adds RAQS and VAV within rooms.
4. The user adds AHUs, EVs and Chillers separately.
5. During equipment creation or editing, the user enters the associated CSV filename.
6. The user manually places all CSV files inside a designated directory.
7. Collia locates the CSV files using their configured filenames.
8. FastAPI reads and processes the corresponding files.
9. The system extracts relevant information.
10. Extracted information is mapped to the correct configured equipment.
11. The processed data becomes available for Knowledge Graph generation.

## 6.2 CSV directory

Use:

data/csv/

All source CSV files must be stored here.

Example:

data/
csv/
RAQS_101.csv
VAV_101.csv
AHU_01.csv
EV_01.csv
Chiller_01.csv

The filenames above are illustrative only.

Do not assume that these are actual Belimo filenames.

## 6.3 Filename association

During equipment creation, provide a field for:

CSV Filename

Example:

Equipment Type: RAQS
Name: Room 101 Air Quality Sensor
Description: Monitors room temperature, humidity and CO₂.
CSV Filename: RAQS_101.csv

The backend must use this filename to locate:

data/csv/RAQS_101.csv

The application should support the following:

- Verify whether the filename exists.
- Display whether the file is available.
- Display whether it has been processed.
- Allow users to update the filename.
- Allow users to rescan the CSV directory.
- Allow users to process the files.
- Report missing files.
- Report invalid CSV formats.
- Report processing errors.

Use safe file-path handling. Filenames must not be allowed to escape the designated CSV directory.

Do not silently substitute a different file when a filename is missing.

## 6.4 CSV processing

Use Pandas for processing.

The system should:

1. Locate the configured file.
2. Read its contents.
3. Inspect column headers.
4. Identify available parameters.
5. Extract relevant readings.
6. Identify timestamps where available.
7. Preserve original column names.
8. Identify missing or unrecognised columns.
9. Validate the extracted information.
10. Associate the extracted information with the configured equipment.

CSV parsing must be modular.

Different equipment categories may require different mapping rules.

Do not assume all files follow the same structure.

Do not modify the original source CSV files.

## 6.5 Configuration persistence

There is no database in the initial architecture.

However, building configurations must persist after restarting the application.

Implement file-based persistence using a structured, versioned CSV-based configuration approach.

The internal configuration format may use multiple CSV files to represent entities and relationships.

Do not use JSON files for persistent configuration.

Separate:

- User-defined configuration.
- Original source CSV files.
- Processed information.
- Generated graph artefacts.

Ensure that configuration updates do not overwrite original source data.

# 7. ENTITY RELATIONSHIPS AND SYSTEM MODELLING

The building hierarchy and the HVAC equipment relationships are not necessarily identical.

For example:

- A building contains multiple floors.
- A floor contains multiple rooms.
- A room may contain RAQS and VAV equipment.
- An AHU may serve multiple rooms.
- A Chiller may supply multiple AHUs.
- An EV may be associated with relevant HVAC equipment.

These examples illustrate possible relationships and must not be treated as automatically established facts.

The system must support relationships beyond simple parent-child containment.

Separate:

1. Structural relationships: building, floor and room containment.
2. Equipment relationships: serves, supplies, controls, measures or connects to.

Where the user defines a relationship, preserve it.

Where CSV data provides evidence for a relationship, identify and validate it.

Do not invent relationships based only on equipment names or assumptions.

Provide a modular relationship model so additional relationship types can be introduced later.

# 8. KNOWLEDGE GRAPH GENERATION

The configured building structure and processed CSV information must jointly form the Knowledge Graph.

Use:

- NetworkX for graph construction and manipulation.
- RDFLib for semantic graph representation.
- PyVis for graph visualisation.
- SHACL / pySHACL for validation when appropriate.

## 8.1 Graph nodes

Initial node categories:

- Building
- Floor
- Room
- RAQS
- VAV
- AHU
- EV
- Chiller

Additional nodes or properties may be introduced when supported by actual data.

## 8.2 Graph relationships

Represent relationships such as:

- Building CONTAINS Floor.
- Floor CONTAINS Room.
- Room HAS_EQUIPMENT RAQS.
- Room HAS_EQUIPMENT VAV.
- AHU SERVES Room.
- Chiller SUPPLIES AHU.
- EV CONNECTED_TO relevant equipment.

These are illustrative relationship types. Only create relationships supported by the configuration or validated source information.

## 8.3 Graph properties

Store relevant information as node properties or associated observations.

Examples:

- Equipment name.
- Equipment description.
- Equipment category.
- Source CSV filename.
- Parameter name.
- Parameter value.
- Unit of measurement.
- Timestamp.

Keep time-series readings distinguishable from static equipment properties.

## 8.4 Graph validation

The graph must be checked for:

- Missing entities.
- Invalid relationships.
- Duplicate identifiers.
- Missing references.
- Inconsistent equipment associations.
- Unsupported relationship types.

The graph must be traceable to its source configuration and CSV data.

# 9. ANOMALY DETECTION

This stage begins after CSV extraction and Knowledge Graph generation are functioning correctly.

Initially implement rule-based anomaly detection.

Examples:

Example 1:
A room temperature reading is significantly higher than its configured setpoint.

Example 2:
An AHU damper command is 100%, but its feedback position is 20%, where both readings are available.

Example 3:
An equipment operating parameter is outside its configured acceptable range.

Requirements:

- Define rules explicitly.
- Support configurable thresholds.
- Consider measurement units.
- Handle missing readings.
- Distinguish abnormal readings from missing data.
- Record the source CSV and relevant timestamp.
- Associate anomalies with the relevant equipment.
- Use Knowledge Graph relationships to identify connected equipment.

Do not introduce machine learning at this stage.

---

# 10. PROBABLE CAUSE ANALYSIS

After anomaly detection, implement probable cause analysis.

The system should:

1. Identify the equipment where the anomaly occurred.
2. Examine its relevant parameters.
3. Inspect associated equipment.
4. Traverse relevant Knowledge Graph relationships.
5. Examine supporting CSV readings.
6. Identify possible contributing factors.
7. Present probable causes with supporting evidence.

Clearly distinguish:

- Directly observed facts.
- Detected anomalies.
- Inferred probable causes.

Do not present an unsupported inference as a confirmed equipment failure.

---

# 11. FAILURE PREDICTION

Introduce failure prediction only after sufficient data and validation are available.

The objective is to identify possible future equipment failures or abnormal operating conditions.

Use historical readings and relevant equipment relationships.

Do not claim predictive accuracy without validation.

Keep the prediction module separate from basic anomaly detection.

---

# 12. SUGGESTED SOLUTIONS

For each detected anomaly and probable cause, provide possible corrective suggestions.

Each suggestion should include:

- Associated anomaly.
- Probable cause.
- Supporting evidence.
- Suggested corrective action.
- Relevant equipment.

Suggestions must be presented as recommendations, not automatic equipment commands.

# 13. OFFLINE LLM CHATBOT

The final major feature is an offline LLM-based chatbot.

Use Ollama for local inference.

The chatbot should provide a natural-language interface to the configured system.

Users should eventually be able to ask questions such as:

- What equipment is present on Floor 2?
- Which rooms are served by AHU 01?
- What anomalies were detected today?
- Why was this equipment flagged?
- What are the possible causes of the AHU anomaly?
- What corrective actions are suggested?
- Show me the relationship between the Chiller and the connected AHUs.

The chatbot must retrieve information from Collia's configuration, processed CSV information, Knowledge Graph and analysis results.

Use retrieval and relevant graph context rather than relying entirely on the LLM's pretrained knowledge.

The chatbot must function without requiring an internet connection.

Do not implement this feature during the initial stages.
